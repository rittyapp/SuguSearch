# 開発ガイド（担当が替わったら最初に読む）

## このガイドについて

**このファイルは別プロジェクト（PACRAFT Flow）で書かれたものを、プロジェクトに依存しない汎用の開発ガイドへ書き直したものです。**
どのプロジェクトにも共通する「進め方」と「Windows + Python + 配布物でハマりやすい点」だけを残してあります。

- **ここに書くこと** … 作業の進め方、環境の落とし穴、事故を繰り返さないための約束事
- **ここに書かないこと** … 特定プロジェクトの仕組み・テスト一覧・リポジトリ名・ファイル構成
  → それぞれのプロジェクトの `architecture.md` / `roadmap.md` / `build.md` に書く

このプロジェクト（すぐサーチ）の場合は [architecture.md](architecture.md)（仕組み）、
[roadmap.md](roadmap.md)（これから作るもの・未解決の疑問）、[../README.MD](../README.MD)（起動とビルド）が対応します。

最終更新: 2026-09-02（複数人配布・個人パスを画面に出さない）

## 0. 複数人で使う前提（必須）

このアプリは **開発者1人用ではない**。社内の複数 PC で使う。

| やってはいけない | 理由 |
|------------------|------|
| UI に `C:\Users\開発者名\...` をそのまま出す | 他人の PC では意味が違う／個人情報に見える |
| 私有 GitHub のまま「トークン必須」で更新させる | 全員にトークンを配ることになる。**Release は公開**にする |
| 開発用パス（`script\setup.bat` 等）を利用者向けメッセージの主文にする | 利用者は配布セットアップだけ知っていればよい |
| 設定やログに他人のマシン固有パスをハードコード | 各 PC の `%LOCALAPPDATA%` を使う |

| 正しい前提 | 内容 |
|------------|------|
| インストール先 | 各ユーザーの `%LOCALAPPDATA%\SuguSearch\`。**ユーザーごとに違うのは正常** |
| 更新の参照先（実装） | 公開の配布サーバ（現状は GitHub Releases）。**利用者 UI に GitHub／トークン／URL を出さない** |
| 画面の言い方 | 「セットアップ済み」「ダウンロードして更新」「ダウンロード可能な版」。開発用語・個人パス禁止 |

利用者は **GitHub を知らなくてよい**。更新タブにトークン欄・GitHub の説明・リポジトリ URL を出さない。  
開発者の PC で見える `C:\Users\...\AppData\...` は LocalAppData であり、他人の PC では別パスになる。

## 1. 進め方

- **本人が実機で確認する。** こちらは「実データで検証してから報告」が基本
- **推測で報告しない。** 「直したはず」ではなく、実行結果を見せる。テストが落ちたなら落ちたと書く
- **だんまり厳禁。** 重い処理はワーカーで回して進捗を出す。無言で終わらせない
- **配布先は PC に詳しくない人**という前提で作る。ルートには押すものだけ置き、エラーは理由を画面に出す
- 挙動を変える前に、**変わらないことをテストで固定してから**直す
- 最も価値のある改善は、**本人が実機で使って出てきた不便**から生まれる。仕様の先回りより、そこを優先する
- **複数人配布を常に意識する。** 個人用のパス・トークン・私有リポ前提のエラーを利用者に見せない（§0）

### 触るときにいちばん気をつけること

| 対象 | 注意 |
|------|------|
| **停止・中断まわり** | 途中で止めたときに**子プロセスが残っていないこと**を実データで確認する（外部ツールを起動する処理は特に） |
| **「止まらない」の意味** | 「全体を止めない（次の対象へ進む）」ことと、「1 件の中で確認できていないのに次工程へ進む」ことは別。後者を許さないテストは**緩めない** |
| **処理ロジックと表示の切り分け** | ファイルに実際に何をするか（判定・順序・出力結果）は勝手に変えない。表示や操作は積極的に良くしてよい |
| **既存データの破壊** | 上書き・移動・削除を伴う処理は、実行前後で**中身のハッシュを突き合わせて**確認する |

## 2. テスト

- 直したら**一通り流す**。速いテストと遅いテストが混ざっている場合、遅い方ほど大事な所を守っていることが多い
- **一番大事なテスト（事故を防いでいるもの）は、通すために緩めない**。落ちたら実装側を直す
- テストデータが git 管理外（サイズが大きい等）なら **消さないこと**。本人が検証用に育てている資産
- 想定と違う結果が出たら、**まず入力データを疑う**。本人が検証中にデータを書き換えていることがある
- Windows の PowerShell からテストを流すときは文字化け対策を入れる

```powershell
$env:PYTHONIOENCODING='utf-8'      # 付けないと cp932 で print が落ちる
```

### 破壊的な処理を実データで通すとき

1. 対象の パス・サイズ・更新時刻・**SHA1** を実行前に記録する
2. 処理を通す
3. 「**中身（SHA1）が実行後にどこにも無いもの**」を数える ← これが「失われた」の定義

種類ごとに分けて数えること。仕様として上書きされるものと、絶対に失ってはいけないものを混ぜない。

## 3. 開発環境の落とし穴（Windows + Python）

ここは繰り返しハマる箇所なので、**消さないこと**。

- **日本語パスは絶対パスで扱う。** Python スクリプトに日本語を含む相対パスを渡すと
  `FileNotFoundError` になることがある（既定コードページの影響）
- **`TCL_LIBRARY` / `TK_LIBRARY` がユーザー環境変数に残っている**と、別バージョンの Tcl/Tk を指して
  tkinter の初期化に失敗する。アプリ側で吸収しておく
  （すぐサーチ では `_fix_tcl_tk_paths()` が `import tkinter` の前に実行される）
- **`python` と `py` で別バージョンが起動することがある。** ビルドに使われるのがどれか確認する
  （`where python` の先頭 / `py -3 -V`）
- PowerShell から一時スクリプトを書き出すときは **UTF-8（BOM 無し）**。
  ヒアドキュメントに日本語を入れると壊れることがある
- **`.bat` は ANSI(CP932) + CRLF 必須。** UTF-8 で保存するとダブルクリックで動かない
  （日本語メッセージが化けている `.bat` を「直そう」として UTF-8 保存すると壊れる）。
  ファイルが CP932 なら先頭は `chcp 932` にしておくとコンソール表示も揃う
- **PyInstaller に `--specpath` を渡すと、`--add-data` などの相対パスが spec の場所を基準に解決される。**
  `--specpath build` を付けた瞬間に `assets\x.ico` が `build\assets\x.ico` を探して失敗した。
  `--specpath` を使うなら **`--icon` / `--add-data` / スクリプトは絶対パスで渡す**
- `.lnk` を作る PowerShell スクリプトは **UTF-8（BOM 付き）**。
  BOM が無いと Windows PowerShell が ANSI として読み、日本語パスが壊れる
- PyInstaller で pywin32 系を使う場合は `--hidden-import` が要る（自動検出されない）

## 4. 「これは仕様」を残す

実データを見て「事故だ」と思う挙動でも、**そう作ってある**ものがある。
プロジェクトごとに「見えるもの / なぜそうなっているか / いつ誰が確認したか」の表を作り、
バグとして直してしまわないようにする。

判断がつかないものは勝手に決めず、**roadmap の「未解決の疑問点」に上げて本人に聞く**。

## 5. git 運用

- 安定版のブランチがどれかを最初に確認する。**古い世代のブランチを触らない**
- 実データ・同梱ランタイム・ビルド生成物・状態ファイルは `.gitignore` に入れる
- コミットは意味のある単位で。挙動を変えるコミットと整形だけのコミットは分ける

## 6. ドラッグ＆ドロップ（Windows・分かっていること）

エクスプローラーへのドラッグ＆ドロップは一度作って**動作が不安定だったため外した**。作り直すとき用のメモ。

- **落ちる場所**: `pythoncom.DoDragDrop()` は UI スレッドをブロックする同期呼び出し。tkinter の
  `<B1-Motion>` ハンドラの中から呼ぶと、環境によってドラッグ中にイベントループが噛み合わず、
  カーソルが戻らない／ドロップ先が反応しない／アプリごと固まる、が起きた
- **`win32com.server.util.wrap` で作った IDataObject / IDropSource** は、`_com_interfaces_` を
  import 順の都合で実行時に差し込む必要があった（この時点でかなり脆い）
- **`win32con` に `DROPEFFECT_*` が無い環境がある**ので数値定数（COPY=1 / MOVE=2 / LINK=4）を直書きしていた
- **クリップボード経由（CF_HDROP + Preferred DropEffect）は安定して動く。** D&D が難しいときは
  「コピー → エクスプローラーで Ctrl+V」で代替できる。実際こちらへ寄せた
- 再挑戦するなら、まず**別プロセス／別スレッドに寄せてイベントループを止めない**設計にすること。
  UI スレッドを直接ブロックする形は同じ所で詰まる

## 7. ビルドと配布

- **完成物は 1 コマンド（またはダブルクリック 1 回）で作れる**状態を保つ
- 本人が触るのはその 1 本だけ。それ以外のスクリプトは裏に置く
- 特に指示がなければ、修正後は**配布物まで更新して**報告する
- 配布物に設定ファイルを作る場合は、**書き込みできる場所**に置かれる前提で設計する

具体的な手順は各プロジェクトの README かビルド用ドキュメントに書く（このプロジェクトは [../README.MD](../README.MD) の「再ビルド」）。
